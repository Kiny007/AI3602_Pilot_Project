# AI 3602 Pilot Project 期末项目先导作业

## 概览
本项目为期末课程项目的先导作业。项目内容是：运用数据挖掘的方法，结合现代 AI 编程工具，在公开的、相对原始的互联网数据集中，挖掘和清洗 **特定选题方向** 的数据。

1. 先导项目要求 **单人** 完成。
2. 先导项目提供 **五个选题方向**，具体要求已全部公布，**任选其一即可**。选题方向包括文本数据（数学领域文本）、流数据、图数据、源代码、隐私信息。
3. 鼓励使用课程中提到的数据挖掘算法；项目也允许使用课程中没有涉及的、数据挖掘相关的算法。
4. 鼓励使用 AI IDE、Vibe Coding 等方式完成该作业。
5. 占课程最终成绩15%。
6. 鼓励将收集的数据集运用到期末项目中，方式不限，如作为 benchmark、训练数据、RAG 知识库等。例如，收集数学题数据集提升Agent解题能力、收集用户关系图数据作为推荐系统的冷启动数据等。

具体的选题、提交、评分详见下文。

## 选题信息（更新完成）
### 选题一：从 webtext 中筛选数学领域的文本

#### 背景

随着大规模语言模型（LLM）在教育、科研与自动推理等任务上的普及，其数学理解与解题能力成为重要瓶颈。当前主流模型的数学推理能力往往受限于训练数据中高质量数学语料的稀缺与噪声。本选题旨在从大规模公开互联网文本（如 fineweb）中，自动筛选出高质量的数学领域文本数据，为后续模型训练、微调或 RAG（检索增强生成）提供数据基础。这些数据可用于：
- 构建数学题生成 / 解析系统的训练语料；
- 提升 LLM 在代数、几何、逻辑推理等任务上的表现；
- 构建数学知识图谱或公式知识库；
- 分析网络上数学相关内容的分布、话题结构等。

#### 选题目标

- 从原始 webtext 中提取出含有明显数学特征的文本片段，例如：
    - 含有数学公式、方程式或符号（如 LaTeX 表达式、数学符号）；
    - 解释数学概念、定义、证明的教学性文字；
    - 与数学学习、考试、推理相关的题干或讨论；
    - 论坛或博客中关于数学方法、算法讨论的内容；
    - 包含数学公式、和数学相关的领域（例如自然科学、物理、计算机算法）等内容。
- 非数学文本（如生活随笔、社会新闻）需被过滤。
- 每条数据建议保留以下字段（最终提交1000条筛选后的文本）：
    - text: 原始文本内容
    - has_formula: 是否检测到公式
    - topic: 数学子领域（如代数、几何、概率论，可由模型或规则推测）

#### 数据来源

- **待筛选数据**必须来自通用网络文本数据集，例如 [FineWeb](https://huggingface.co/datasets/HuggingFaceFW/fineweb)。最终提交的数学文本须由自己的方法从这些通用文本中筛选得到。
- **参考数据**可使用 [OpenWebMath](https://huggingface.co/datasets/open-web-math/open-web-math) 等数学专用语料，例如用于相似度匹配。数学专用语料不能作为本题的待筛选数据。

#### 推荐方法

- high-dim data 章节介绍的相关方法（如利用 open-web-math 等参考数据集进行相似项查找）
- 特征提取：基于关键词（如“equation”, “proof”, “公式”, “方程”等）或正则检测数学符号。
- 向量表示：用文本嵌入模型（如 qwen3-embedding、fasttext）计算语义相似度，筛选与数学语料相近的文本。


#### 评估指标（完成性指标）

- 筛选精确度：人工抽样判定（汇报的数据集中的数学相关文本比例高于60%）。
    - **人工抽样判定数学相关文本比例在 60% 左右（或更高），即视为满分。**
    - 如果多次抽样比例均显著低于 50%，将酌情扣分。
- 抽取真实性：助教复现代码后抽取结果和汇报结果基本一致。
    - 如复现结果和汇报结果有明显差异，将酌情扣分。
- ~~数据多样性（拓展指标）~~
    - 先导项目评分过程中，不考虑数据多样性或其他拓展指标，后续的拓展和提升可以作为期末项目的内容。

### 选题二：社交媒体实时水军识别

#### 背景

在社交媒体平台上，水军（或称为“僵尸粉”、“营销号”）通过发布大量重复、高度相似或协同出现的内容，试图操控舆论、制造虚假热度。这类行为严重干扰了信息生态的真实性和公平性。

#### 选题目标

实现一个实时分析代码，从持续到达的社交媒体文本流中，识别出疑似水军账号的异常推文，具体定义为：

- 一段时间内多个账号发布围绕相同话题、内容高度类同的信息
- 该任务可用于：
    - 监控社交媒体中虚假热度
    - 社交平台内容审核模块的前置过滤；
    - 为后续使用机器学习方法分析账号提供目标数据集。

#### 数据来源

- 可自由选定开源社交媒体数据集（无人工标注），例如 [enryu43/twitter100m_tweets](https://huggingface.co/datasets/enryu43/twitter100m_tweets)。**该数据集仅作为示例，不保证适用于本任务；同学们可自行寻找并选择适合本任务的开源数据集。**
    - 该数据集的字段对应关系：`tweet` 为文本，`user` 为用户名（用于区分用户），`date` 为发帖时间；`id` 为帖子 ID，不是用户 ID。
    - 原始记录不保证按时间升序排列，使用前需按 `date` 排序，再按时间顺序模拟流式输入。
- 也可以自行爬取社交媒体实时信息（注意网站爬虫规定）

两种方式都可以按平台、话题或时间段选取原始帖文。疑似水军帖文组须由自己的程序在流式处理过程中识别得到。

#### 方法

- 识别算法要求
    - 按时间顺序读取数据，分析过程中的窗口大小（同时能分析的帖文数量）为
    $$min(总数据量的5\%, 500)$$
- 输出的数据
    - N组疑似水军的帖文组，每组包含至少M个帖文，且每组至少有L个不同用户。

#### 评估指标

- 完成性：$N \ge 5, M \ge 5，L \ge 3$。
    - 达到完成性指标即视为满分 100 分。
    - 代码可复现，$N \ge 1, M \ge 1, L \ge 1$，即视为 90 分。
    - 其他情况人工评分。
- 可复现性：代码复现结果与汇报结果基本一致。
    - 如复现结果和汇报结果有明显差异，将酌情扣分。
- ~~拓展性：尝试在真实社交媒体中爬取帖文进行分析~~
    - 先导项目评分过程中，不考虑数据多样性或其他拓展指标，后续的拓展和提升可以作为期末项目的内容。

### 选题三：基于知识图谱的 Acemap 搜索增强

#### 背景

知识图谱通过 `(subject, relation, object)` 三元组表示实体或概念之间的关系，可用于发现搜索关键词的相关概念，为学术文献搜索提供辅助信息。

[Acemap](https://acemap.info/) 是一个基于多个学科领域的海量学术资源构建的数据库。除了数据库之外，Acemap 主页提供了一个配套的搜索引擎。目前，Acemap 中的文献检索功能基于 ElasticSearch 和关系型数据库。由于 ElasticSearch 的默认检索功能主要基于关键词匹配，返回的结果有时可能不够全面，有时则包含与用户搜索意图无关的内容。

我们考虑通过知识图谱对 Acemap 的搜索功能进行增强。Acemap 支持搜索关键词、作者、机构等。为了简化任务，只需选择 **一个学科或研究领域的关键词搜索** 进行增强。搜索的工作流程是：

1. 用户输入关键词
2. 根据关键词，返回若干篇匹配的文献/学术概念

#### 选题目标

本项目的目标是：在 Acemap 现有的搜索系统上，基于知识图谱，增加一个 “预处理” 或 “后处理” 过程，使 Acemap 搜索功能返回的结果更加准确、丰富、完善。

可以参考的思路包括但不限于

- **从提高搜索精度的角度**：利用知识图谱对搜索结果进行筛选（例如，如果某篇文章的关键词不在用户搜索关键词的临近节点内，则降低该条目的排名或将其移除）。
- **从召回相关知识的角度**：引入知识图谱，在正式搜索前，用知识图谱找到用户输入的关键词的 **相关概念**，然后调用搜索接口，返回更多相关文献。
- **从增强搜索结果的角度**：在搜索结束后，用首次搜索的结果，结合知识图谱（或其他搜索接口）对结果进行增强，返回“多跳搜索”的相关工作（例如相同作者、相同机构、相同合作者的相关领域工作）。
- **搜索意图理解**：ElasticSearch 的搜索以关键词匹配为主，因此无法处理类似 "recent research results on plate tectonics" 的非关键词查询。可尝试结合知识图谱与意图理解模型，处理用户的搜索意图。
- **其他思路**：本先导项目以完成性目标为主，我们鼓励同学们结合可用的数据，探索各类方案。

#### 数据来源

- Acemap 的主要搜索接口：
    - 论文搜索：`https://acemap.info/api/v1/work/search`
        - 样例：`https://acemap.info/api/v1/work/search?keyword=rock&order=desc&page=1&size=10`，搜索关键词 `rock`，每页 10 个结果，返回第 1 页，按相关性降序排序。
        - 可将该 URL 复制到浏览器地址栏获取 Response。
    - 作者搜索：`https://acemap.info/api/v1/author/search`
        - 样例：`https://acemap.info/api/v1/author/search?keyword=john&page=1&size=10`，搜索关键词 `john`，每页 10 个结果，返回第 1 页。
    - 机构搜索：`https://acemap.info/api/v1/institution/search`
        - 样例：`https://acemap.info/api/v1/institution/search?keyword=jiaotong%20university&page=1&size=10`，搜索关键词 `jiaotong university`，每页 10 个结果，返回第 1 页。
    - 实际开发时，可以使用 Python 的 `requests` （或其他类似的库）发送 HTTP 请求。
        - **请求头提示**：实测中，使用 `requests` 默认的 User-Agent 请求 Acemap 接口可能返回 403。建议通过 `headers` 参数显式设置程序标识，例如 `requests.get(url, headers={"User-Agent": "AI3602-PilotProject/1.0"}, timeout=20)`。User-Agent 的值可使用自己的程序名称和版本号，不必与示例完全一致。
- [ConceptNet](https://conceptnet.io/) 提供了更广泛、全面的知识图谱。
    - 可以针对特定领域，从 ConceptNet 抽取子图，作为搜索时的知识增强。
    - **优先使用离线数据**：获取方式见 [ConceptNet 官方下载说明](https://github.com/commonsense/conceptnet5/wiki/Downloads)。下载后，可在本地抽取所选领域的相关子图，用于搜索增强。
    - **网页查询示例**：可通过 [rock 概念页面](https://conceptnet.io/c/en/rock)浏览概念及其关系。该页面用于网页浏览，返回的是 HTML，不能直接替代返回 JSON 数据的在线 API。
    - **在线 API 可用性说明**：ConceptNet 在线 API 曾多次出现 502 错误，使用时可能不可用，建议不要将其作为完成作业的必要依赖；网页能够打开也不代表在线 API 可用。
- 也可以搜集其他特定领域的、开源的知识图谱。

围绕所选的一个学科或研究领域，可以直接使用已有的开源领域知识图谱，也可以从通用知识图谱中抽取相关子图。须自行实现利用图谱增强 Acemap 搜索的步骤。

#### 推荐方法

- 参考选题目标中建议的方法

#### 评估指标（完成性指标）

- 功能完备性：一个可复现的代码或脚本。在现有搜索 API 的基础上，**完成至少一项增强设计，且搜索常见关键词时不报错，即视为满分**（先导项目以功能实现为主，不设额外的性能或指标要求）。
- 数据收集：与搜索功能配套的数据或增强功能（知识图谱子图、作者机构信息等）

### 选题四：代码项目编程规范的自动挖掘

#### 背景

成熟的软件项目背后通常有一套约定俗成的编程规范或最佳实践。这些规则涵盖了从命名方式（*变量名统一使用 `snake_case`，类名统一使用 `PascalCase`*），到编程范式和规定（*使用 `pydantic` 的 `BaseModel` 定义 HTTP 请求和响应的格式，并提供类型标注*）。相关的规则可能会写在开发文档中，也可能只是项目维护者之间心照不宣的共识。

如今，随着 AI 辅助编程的快速普及，AI IDE 通常也支持用户将这些规范和共识以“规则（Rule）”的形式注入大模型（例如，Cursor 允许用户定义一系列 [Rules](https://cursor.com/docs/rules)，视情况为大模型引入一系列编程规则和要求）。这些 Rule 以特定格式的文本文档记录，AI IDE 会在符合条件时加载并应用这些规则。

尽管通用的规则可以通过网络共享，其他与特定项目高度相关的规则目前仍然比较依赖人工维护。由于规则类型、粒度的多样性，以及其与项目代码的强关联性，传统的静态代码分析工具很难全面地总结这些规则。然而，代码大模型具备分析和理解自然语言和程序语言的能力，有潜力从中学习到项目中隐含的编程规则和最佳实践。

在本项目中，我们希望结合源代码分析技术和大语言模型，从开源仓库中自动挖掘和总结项目级的编程规范与代码最佳实践。

#### 选题目标

本项目的目标是：构建一个基于代码分析或代码语言模型的系统，该系统能从 Python（或其他语言）项目中，自动挖掘项目级别的、自然语言的编程规则和开发规范。

#### 数据来源

规则挖掘的数据来源主要为 GitHub （或其他类似的代码托管平台）的开源项目。建议选择质量较高的开源项目。

- 可以通过 API 从 GitHub 上下载开源项目代码；也可以选用 [CodeSearchNet](https://huggingface.co/datasets/code-search-net/code_search_net)、[The Stack](https://huggingface.co/datasets/bigcode/the-stack) 等通用代码数据集。
    - The Stack 需要登录 Hugging Face 并接受数据集访问条件后才能访问数据文件；通过代码下载时需使用具备访问权限的账号进行认证。
    - 除了源代码数据之外，Commit 中的代码修改记录、Pull Request 中的交流讨论、GitHub Actions 中的 CI/CD 配置，也可以作为规则挖掘的依据。
- 提交的规则必须从代码项目中挖掘得到，可以将公开的规则用作少样本学习，但禁止直接提交公开的规则集合。

#### 推荐方法

- **基于 AST 的代码分析.** 可以尝试直接解析项目源代码，从中总结常见的、抽象的代码结构，并进一步从中挖掘规则。
- **基于代码语言模型/大语言模型的规则总结.** 现代代码语言模型或通用大模型具备良好的上下文理解能力，可以尝试利用大模型总结和归纳规则。
    - 如果考虑本地部署模型，视显存大小，可考虑 CodeGen-350M / Qwen3-0.6B / CodeGen-2B / CodeGen-6B / Qwen3-8B / Qwen3-Coder-30B-A3B 等。
    - 允许使用商用大模型 API。但是请留意商用模型的成本（成本不作为评分指标）。
- **Commit 记录的对比.** 可以尝试对比代码提交记录（例如字符串或 AST 的编辑），从中总结规则。
- **Pull Request（PR）中的 Code Review 记录.** 开源项目的 PR 通常需要经过开发者 review 后才能合并到主分支。在 PR 的讨论记录中，可能存在 reviewer 对代码风格或编程规范的建议。
- 也可以采用其他方法，或者上述方案的结合。

#### 评估指标（完成性指标）

- 功能完备性：用于挖掘规则的、可复现的代码或脚本。
- 数据量：提交来自不同开源项目的、自动挖掘的至少 25 条规则，以及对应的 GitHub 仓库链接。
    - GitHub 仓库使用的编程语言不限。规则可以是中文或英文。
    - 可参考 Cursor Rule 的格式，规则可以存放在多个文件中，每个文件中可包含多条规则。
    - 不同项目下挖掘的规则，即使文本内容类似，如果作用范围（项目、模块、文件等）不同，则视为不同规则。
- 规则粒度（评分细则见下方表格）
    - **建议** 关注项目级别的、与项目中的特定文件、模块或功能相关的规则（针对特定项目，或者针对项目下的特定模块）。例如 “*在 `models` 模块中，优先使用 sci-kit learn 的机器学习类，仅在需要深度神经网络或 GPU 加速时使用 PyTorch*”、“*在 `api/v1` 目录下的后端 API 中，API 接口使用 `snake_case` 命名*”。满分要求至少有 **12 条**规则符合此条件，由 LLM-as-a-Judge 结合人工检查评定。
    - **不建议** 过于笼统的通用规则。例如 “*你是一个专业的 Python 程序员*”，或者笼统地 “*（对所有文件）使用 `snake_case` 命名*”、“*使用模块化设计，核心功能、单元测试、文档放在不同目录下*”。
    - **不计入完成度：** 仅涉及通用代码格式或基础代码检查的规则，例如“函数之间空两行”“删除未使用的变量”。如果一条规则反映了项目在特定模块或功能中实际采用的约定，即使可以用静态分析工具检查，也可以计入。
- 可复现性：代码复现结果与汇报结果基本一致。

| 评分标准                                                                 | 分值            |
| ------------------------------------------------------------------------ | --------------- |
| 代码可复现；产出至少 25 条规则，其中至少 12 条符合 “建议” 条件   | 100             |
| 代码可复现；未达到满分条件，但产出至少 12 条符合 “建议” 条件的规则       | 90              |
| 代码可复现；产出至少 5 条符合 “建议” 条件的规则，但是不足 12 条          | 70-90，人工评分 |
| 代码可复现；未达成更高评分标准的条件，但是人工评阅认为基本功能或思路完善 | 60-70，人工评分 |
| 其他情况                                                                         |        人工评分         |

### 选题五：Reddit 用户隐私信息挖掘

#### 背景

在当下的开放社区（如 Reddit）中，用户会在发帖或评论中自愿或无意透露大量与个人相关的隐私信息，例如年龄、家庭情况、教育背景、疾病史、收入等。这些信息对用户画像、广告定向、舆情分析等任务具有重要作用，同时也带来潜在隐私泄露风险。

本选题允许通过在线采集或自行选择公开原始数据集两种方式获取真实的 Reddit 帖子，并利用 AI workflow 工具（如 n8n、LangFlow、Flowise、Zapier with LLMs）构建一个自动化工作流或者 AI Agent，自动识别并标注隐私类别，从而构建一个原创的 Reddit 隐私信息数据集。

#### 选题目标

使用 AI workflow 工具（或其他自动化方法）自动化地完成隐私数据挖掘 pipeline。

Pipeline 的参考工作流程为：

1. **数据获取。** 可通过以下任一方式获取真实的 Reddit 帖文。两种方式均须以通用帖文数据作为待筛选输入，即这些帖文在进入筛选流程前，未经针对隐私披露的专门筛选或标注。
    - **在线采集。** 自行采集 Reddit 社区的原始帖文，遵守所用平台或接口的访问要求。可以选定社区和时间段，例如采集某个生活分享类 subreddit 在一段时间内发布的帖文。
    - **公开数据集。** 自行选择并读取公开的通用 Reddit 帖文数据集。

    两种方式均须使用自己的方法，从原始帖文中筛选出披露个人信息的文本并标注隐私类别，并在报告中说明数据来源及获取方式。
2. **初步筛选.** 排除明显和个人信息无关的内容（例如评论他人、时事新闻等）。
3. **模型识别.** 筛选并识别个人信息实体。方法不限（例如传统自然语言处理、命名实体识别、基于大模型的信息抽取等）。
4. **（可选）数据清洗.** 人工或 LLM-as-a-Judge 复查并优化前述工作流。
5. **输出.** 保存结果。

本选题下定义的隐私信息类别包括：

- SCH（Education）： 学历、就读学校、学位等
- OCC（Occupation）： 职业、工作状态
- MAR（Marital Status）： 婚姻/恋爱状态
- LOC（Location）： 所在地、去过的地点（排除商场/办公楼等功能性地点）
- INC（Income）： 收入、经济状况
- HEA（Health）： 身体/心理健康信息、用药信息
- FAM（Family）： 家庭成员信息
- APP（Appearance）： 外貌、身材、风格描述
- SEX（Sex）： 性别、妊娠等
- POB（Place of Birth）： 出生地、家乡
- AGE（Age）： 年龄、年龄阶段
- NAM（Name）： 帖文中提及的非用户ID的姓名

每条数据建议保留以下字段（最终提交至少50条筛选后的文本）：

- text: 原始文本内容（只考虑文本内容。图片等多模态信息不作为先导项目评分标准，可在后续课程项目中深入考虑）
- link: 原帖链接；若原始数据集未提供链接，可记录数据集来源及帖文记录 ID，以便追溯
- privacy_tag: 包含的隐私信息类别

#### 推荐方法

- 关键词过滤（较宽泛筛选）
    Example：occupation: “my job”, “I work at”
- 嵌入相似度（可选）
    基于 embedding 搜索相似文本
- 大模型识别（核心）
    LLM 分类隐私类别
